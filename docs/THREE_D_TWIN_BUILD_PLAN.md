# 3D viewer and digital-twin build plan

This plan turns the existing model viewer into a defensible digital-twin surface without treating public or demonstration geometry as maintenance-authoritative data.

## Current spine

| Capability | Current contract | State |
| --- | --- | --- |
| Local reference models | `3d-viewer/models.json` | Working; bundled demonstration assets |
| NASA reference library | `3d-viewer/nasa-models.json` plus `3d-viewer/nasa-aeronautics-models.json`, presented through one NASA filter | Working; searchable, lazy-loaded, reference-only, including three direct research-aircraft GLBs |
| OpenVSP Airshow library | `3d-viewer/openvsp-models.json` generated from the public Airshow catalog | Working; community-contributed X3D geometry converted in-browser, searchable, lazy-loaded, simulation/reference-only |
| Smithsonian Air & Space library | `3d-viewer/smithsonian-models.json` generated from the official Smithsonian 3D API | Working; seven aircraft/spacecraft packages, searchable, lazy-loaded, CC0 reference-only |
| FlightGear simulation library | `3d-viewer/flightgear-models.json` generated from a pinned FGx repository revision | Working; five curated aircraft converted client-side from legacy Three.js JSON, simulation/reference-only |
| Tenant model list | `GET /api/digital-twin/models` | Working; authenticated and tenant-scoped, newest 100 |
| Tenant GLB upload | `POST /api/digital-twin/models` with a raw `model/gltf-binary` body | Working; 20 bytes–100 MiB, GLB v2 only |
| Tenant model content | `GET /api/digital-twin/models/{model_id}/content` | Working; tenant-scoped, private cache, content-hash ETag |
| Browser highlight state | `GET/PUT /api/digital-twin/highlight` | Working; tenant/user-scoped |
| Model discovery for the model | `mxg.digital_twin.list_models` | Working; tenant uploads only |
| Mesh/zone highlight | `mxg.digital_twin.highlight_zone` | Working; selectors are checked against the parsed mesh manifest |
| Component operational context | `mxg.digital_twin.component_state` | Limited; case history is available, canonical installation data is not |
| Document links | `mxg.digital_twin.link_documents` | Limited; evidence lookup exists, diagram-to-mesh mapping does not |
| Case markers | `mxg.digital_twin.attach_case_marker` | Working; confirmation required |

The upload path validates the GLB header, declared length, JSON chunk, and the presence of selectable mesh nodes. It stores the file as tenant-owned PostgreSQL `bytea`, derives a SHA-256 content hash, parses a mesh manifest, and deduplicates identical bytes per tenant. Uploading identical bytes updates the existing record's display metadata.

## Boundary decisions

- A **reference model** is geometry that can be inspected but has no operational authority. NASA, OpenVSP Airshow, Smithsonian, and FlightGear simulation models stay in this class until explicitly imported and mapped.
- A **tenant model** is an authenticated copy owned by one organization. Tenant ownership alone does not make it a validated aircraft twin.
- A **mapped twin** binds model and mesh identifiers to canonical aircraft, installation, component, zone, and evidence records.
- A **validated twin** has a reviewed mapping revision and approved applicability. Only this class may drive maintenance assertions without a visible qualification.
- External imports must use provider identifiers from an allowlisted catalog. The server must never fetch an arbitrary browser-supplied URL.

## Build waves

### Wave 1 — Reference catalog and session foundation

- Keep the NASA, OpenVSP Airshow, Smithsonian, and FlightGear manifests generated by their sync scripts; retain each source record's revision or update time in every generated catalog.
- Search and filter by source and size without adding all reference models to the primary model selector.
- Stream a selected GLB only on demand and label it `reference_asset` / `unmapped` in the viewer and maintenance HUD.
- Use the parent application's same-origin session when the viewer is embedded.
- Add a protected standalone viewer entry or an explicit application session broker before relying on direct viewer URLs for authenticated operations.

Acceptance gate: a NASA, OpenVSP Airshow, Smithsonian, or FlightGear simulation model can be found, opened, inspected, and clearly distinguished from a tenant upload or validated twin; no tenant data is written.

### Wave 2 — Controlled import with provenance

- Add immutable import provenance to the persistence model: provider, provider asset ID, source revision, source URL, usage URL, source hash, source byte size, imported timestamp, and importer.
- Add operational classification fields separate from upload provenance: `reference`, `tenant_model`, `mapped`, and `validated`.
- Add `POST /api/digital-twin/imports` accepting a provider and provider asset ID, never an arbitrary URL.
- Resolve the current catalog entry server-side, allowlist the official host/repository, enforce redirect, timeout, media-type, size, and GLB checks, calculate SHA-256, and store the original source revision.
- Return the same model DTO used by the existing tenant list so the viewer can switch to the tenant-owned copy immediately.
- Keep import as an explicit authenticated application action. If later exposed through MCP, require a human-confirmed proposal before writing.

Acceptance gate: an imported model has reproducible provenance, cannot be sourced through SSRF, is deduplicated per tenant, and remains visibly unvalidated until mapped.

### Wave 3 — Canonical aircraft and component mapping

- Add versioned model applicability records for aircraft type/model, serial or tail constraints, and configuration revision.
- Add versioned mesh mappings from `model_id + mesh_id` to canonical component, part number, installation zone, and optional parent assembly.
- Preserve mapping review state, author, reviewer, evidence, effective date, and supersession history.
- Replace free-text mesh matching with stable imported mesh/node identifiers and explicit aliases.
- Expose mapped component lists for accessible keyboard navigation and non-raycast selection.

Acceptance gate: each mapped selection resolves to one auditable component/installation record or returns an explicit ambiguity; no geometry name becomes operational truth by inference.

### Wave 4 — Evidence, procedures, and case rail

- Resolve manual sections, figures, task cards, observations, and evidence against the canonical mapping rather than the raw mesh name.
- Add zone/document fallback when an applicable procedure has no mesh-level mapping.
- Join selected components to open cases and confirmed case markers.
- Add camera presets or computed bounds for evidence-linked areas.
- Keep observation, interpretation, and recommended action visually separate in the HUD.

Acceptance gate: every operational card identifies its source, mapping revision, applicability, confidence basis, and case context.

### Wave 5 — Thermal mount assembly and authored behavior

- Create the thermal mount assembly as an owned tenant/reference asset with explicit subassembly and fastener identifiers.
- Author exploded-view animation, assembly order, reset points, and procedure-media timecodes.
- Bind FLIR/Pi sensor context through bounded target state; do not make raw thermal frames part of the geometry catalog.
- Add mesh-level procedure cues and reversible inspection highlights.

Acceptance gate: the mount can be assembled/exploded consistently on desktop and XR, and each procedure cue resolves to the same mapped part identity.

### Wave 6 — Performance, offline behavior, and release gates

- Generate thumbnails and lightweight preview metadata during catalog sync or import.
- Add download progress, cancellation, retry, cache budgets, and explicit very-heavy model warnings.
- Add LOD/mesh compression policy and test representative desktop, iOS, and Quest memory budgets.
- Define offline behavior: bundled models remain available; remote references report unavailable; tenant models use only an approved private cache policy.
- Add catalog integrity, GLB validation, tenant-isolation, provenance, mapping, accessibility, WebXR, and end-to-end import tests.

Acceptance gate: the viewer meets target device frame/memory budgets, never crosses tenant boundaries, and fails closed on unknown provenance or mapping state.

## Immediate next implementation slice

1. Add the provenance migration and response fields without changing existing model IDs or content URLs.
2. Implement allowlisted NASA and Smithsonian import providers behind `POST /api/digital-twin/imports`; keep FlightGear simulation references out of the import path until per-aircraft rights are reviewed.
3. Add an **Import to tenant** control only after that endpoint passes tenant-isolation, redirect, size, hash, and provenance tests.
4. Add versioned aircraft/component mapping tables and a small mapping editor for the thermal mount assembly.
5. Connect mapped selections to documents and case context, then author the exploded-view sequence.

## Known release blockers outside this slice

- The standalone scene authentication/return flow still needs to be made explicit; the embedded viewer now uses the parent application's same-origin session.
- Repository-wide Rust formatting debt and one existing Clippy `too_many_arguments` finding are separate from this frontend/catalog work.
- Existing MCP registry-count documentation and probes contain known stale counts and should be corrected in their own MCP cleanup change.
